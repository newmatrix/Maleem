# قائمة فحص الإصدار

الإصدار يتم عبر GitHub Releases؛ الـ workflow `Build release` يبني الـ APK الموقّع ويحدّث `update.json` تلقائيًا.

## قبل النشر
1. `node tools/build-www.cjs --check` و`node tools/code-map.cjs --check` و`node tools/build-locales.cjs --check` ← بلا فروق.
2. `npm test --prefix tests` ← أخضر (المتصفح + تغطية الترجمة + lint). اختبار Kotlin يعمل في الـ CI.
3. ارفع التعديلات إلى `main` وانتظر **Web regression tests** أخضر في تبويب Actions. إن فشلت خطوة `native-parser` بسبب تحميل Kotlin من GitHub (504)، أعد تشغيلها.
4. **لا ترفع** `update.json` و`rates.json` من نسختك المحلية: الـ workflow هو من يكتبهما.
5. جرّب على موبايل حقيقي ما تغيّر (التذكيرات والويدجت وإشعارات البنك وDrive لا تُختبر في المتصفح).

## النشر
1. Releases ← **Draft a new release**.
2. Tag جديد بصيغة `vX.Y.Z` (يصير اسم الإصدار). رقم النسخة الداخلي (`versionCode`) = رقم تشغيل الـ workflow + 100، ولا يحتاج تعديلًا.
3. وصف الإصدار هو «إيه الجديد» الذي يراه المستخدم داخل التطبيق (حتى 1500 حرف). اكتبه بالمصري، نقاط قصيرة بإيموجي، وآخر سطر «مليم مجاني تمامًا وبدون إعلانات».
4. **Publish.** انتظر تشغيل `Build release` أخضر؛ يرفق الـ APK بالإصدار ويحدّث `update.json`.

## بعد النشر
- افتح التطبيق على موبايل بإصدار أقدم: يجب أن يعرض نافذة التحديث بالوصف الصحيح، ويحمّل ويثبّت.
- `update.json` ← `latest.code` يساوي رقم الإصدار الجديد، و`sha256` موجود (التحديث مرفوض بدونه).
- رسالة المطوّر لكل المستخدمين: عدّل `message.id` و`message.text` في `update.json` (تظهر مرة واحدة لكل `id`). مثال: `msg-002`.
- لإجبار التحديث: ارفع `minCode` إلى `versionCode` الإصدار المطلوب.

## تراجع
أنشئ إصدارًا جديدًا (لا تحذف القديم) بنفس الكود المصلّح؛ أرقام الإصدار لا ترجع للخلف. لا تعدّل `update.json` يدويًا لتأشير نسخة أقدم.
